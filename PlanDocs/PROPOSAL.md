# DIR-006 提案：Vultr 自建 Linux 中继与 LanChat 远程通信

> 日期：2026-11-16；轮次：2；提案方：Codex；待审核方：Grok；本轮按第 1 轮 REVIEW 修订。
> 工作分支：`codex/non-lan-network`；分支 HEAD：`79e3a92`，相对 `69b5310` 只含 `.claude/` 文档变化；源码同 `69b5310`，稳定标签 `Lanchat-v1.5`；当前程序版本：`2.0.15`。PlanDocs 本题文档仍为工作区改动。
> 用户已选择自建 Vultr 服务器方向，本轮授权是编写方案并交接评审；不代表详细协议已采纳或代码实施已开始。此前 Cloudflare 免费平台建议已被本方案替代。

## 要决定的问题

在保留现有无服务器局域网功能的基础上，如何通过用户自有的一台低配 Vultr Linux 服务器，实现不同公司 Wi-Fi、不同局域网以及公司与家庭电脑之间的文字和文件收发，同时保持客户端轻量、跨平台协议一致、费用可控和可维护。

本轮请审核以下决定与实施顺序，特别关注：

1. 约 5 美元档共享 CPU 服务器是否适合作为小规模起步配置，哪些指标需要实测。
2. 服务端采用 Python 标准库，远程通道优先采用 TLS TCP 长连接，是否比沿用 Cloudflare 的 WebSocket 技术更符合当前项目约束。
3. 设备认证、联系人授权、远程身份、消息确认、重连及文件背压的最小边界是否完整。
4. Windows 原生构建、Linux C# 和 Python 标准库版本能否按同一契约实现，阶段验收是否足以发现跨端退化。

## 建议决定

### 1. 部署与费用边界

- 使用一台 Vultr Shared CPU Linux 实例作为常驻中继，不需要 GPU。建议起步目标为 **1 vCPU、1 GB 内存、约 20 GB 或以上系统盘、可供两端访问的公网 IPv4**；这是本案的容量建议，不是对当前 5 美元套餐规格的承诺。
- 系统优先选择仍受支持的 Debian 或 Ubuntu LTS 最小安装。机房依据公司、家庭两端的真实延迟、丢包和长连接稳定性选择，不仅依据地理距离。
- 约 5 美元/月是用户的实例预算目标。Grok 第 1 轮审核记录已打开公开价格页，Regular Performance 有 **1 vCPU / 1 GB 内存 / 25 GB 存储 / 1.00 TB 流量 / 5 美元每月**这一档；这是审核方核对的公开标价，不是用户账户成交价。Codex 本轮重试价格页仍为 403，未独立复现页面内容；不能再由访问受限推断公开规格不可知。实际可购配置、机房库存、IPv4、税费、备份及其他附加项仍以控制台结算为准，不创建付费资源。[V3]
- 中继主要消耗网络带宽和流量，其次是 TLS 与连接管理资源。首版只转发在线消息和文件，服务端不保存聊天正文与文件副本，磁盘主要用于系统、设备授权元数据和受限日志。
- 单个大小为 S 的文件转发给一个接收者，服务器约接收 S、发出 S，另有协议开销；转给 N 个接收者，出站约为 N×S。网卡收发总量与服务商计费出站量分开核算，不能把它们混为一谈。[V1][V2]
- 首版是单节点服务，服务器重启或故障会中断远程功能。局域网功能继续运行；不宣称高可用或不限量传输。

### 2. 通信结构与技术选择

```text
同一局域网：客户端 A ←→ 原有 UDP 发现 / LANC TCP 直连 ←→ 客户端 B
跨网络：    客户端 A ←→ TLS 长连接 ←→ 自有 Linux 中继 ←→ TLS 长连接 ←→ 客户端 B
```

- 保留 Cloudflare 建议中的“客户端主动连接公网中继”结构；服务端运行在自己的 VPS，不依赖 Workers、Durable Objects、Cloudflare Tunnel 或免费平台额度。
- **优先采用 TLS TCP 长连接**：C# 用系统 `SslStream`，Python 用标准库 `ssl`；服务端初步采用 Python 3 标准库 `asyncio`、`ssl`、`json`，不以 Docker、Nginx、Redis、第三方消息框架或数据库服务为前置依赖。
- 理由：自有 VPS 可直接监听 TCP，无须受平台 WebSocket 接口约束；现有 Windows 强调 C# 5.0 / 老 Framework 兼容，Python 客户端强调纯标准库。TLS TCP 有利于同时维持这些要求。尚未完成运行时与 TLS 1.2 互通实测，不能从 csc 路径中的 `v4.0.30319` 推断实际安装的 Framework 版本。[T1]
- 建议业务端口先使用 TCP 443，须确认该端口未被占用；**TLS TCP 使用 443 不等于 HTTPS**，不保证能通过只允许 HTTP 代理或检查应用协议的公司网络。第一阶段必须在公司与家庭真实网络验证。若被阻断，再评审 WSS 或 HTTPS 通道，不在首版并行实现两套远程传输。
- 服务器应使用受客户端信任、名称匹配、可自动续期的证书；首选用户已有域名或子域名配合公认 CA。若没有域名，IP 证书或证书固定方案另行核实，不用关闭证书验证来代替证书方案。
- 远程通道遵循系统路由；原有 `GetLocalEndpointForTarget` 的物理网卡优先绑定仅用于现有 LAN 路径，不能直接套到公网出口。

### 3. 首版功能、身份和联系人

- 默认仍为局域网模式；远程模式需用户主动启用、填写服务器地址并导入设备凭据。关闭远程模式后不再向公网连接；没有服务器时原有 LAN 功能可独立使用。
- 第一阶段产品范围为少量预登记设备之间的在线私聊。暂以一个私有空间最多 10 台设备、一个设备一条在线连接作为提议上限；正式参数在验证阶段确定。服务端只下发同空间获授权的联系人，不提供公网用户扫描。
- 同一授权设备的新连接认证成功后，**原子替换旧连接**，不等待旧连接的 90 秒失联阈值，也不将“该设备已有连接”当作认证失败。先验证有效凭据，再替换路由；旧连接关闭回调不得删除新连接或把新连接标离线，应按连接代次/实例核对归属。旧连接上已提交但尚无对端 ACK 的文字标为结果未知，不自动重放。被替换的客户端收到明确的会话被替换原因后停止自动抢占重连；正常换网/唤醒由当前唯一重连流程恢复连接。
- 复制包含远程身份和凭据的便携目录不产生新设备；两份副本可能相互替换连接。不同电脑应分别登记凭据，配置/导入入口须明确提示这一行为，并在阶段 2 验证同设备重复登录不会进入无限互抢循环。
- 由管理员在服务器上登记设备、分配空间和独立随机令牌，再通过受信任方式导入客户端。令牌至少含 32 字节安全随机数；不使用公共共享密码、六位房间号或仅凭昵称/IP 的认证。无公开注册网站和短邀请码流程。
- 服务端只存令牌校验摘要及设备授权信息；令牌只在 TLS 建立后用于认证，不写入仓库、URL或普通日志。服务器端管理操作不暴露为无保护的公网接口。凭据轮换/吊销必须断开旧连接，并在重连时拒绝旧凭据。
- 远程 `DeviceId` 持久化，昵称可修改但不改变身份。现有 `NetworkService.LocalId` 每次启动随机生成，继续保持 LAN 行为，不能直接充当远程永久账号。
- 远程会话键必须包含稳定服务器标识、空间标识和设备标识，使用可安全落盘且无歧义的规范格式；不以服务器 IP 或昵称充当永久身份。阶段 2 选型时检查键到历史文件名的完整映射：不能仅依赖 `GetFileNameForSession` 将 `:`、`/`、`\` 折为 `_`，应使用分隔无歧义的规范编码，并验证不同远程键、不同服务器/空间与既有 LAN 键不会写入同一历史文件。同一设备在两种模式下首版允许显示为两个明确标识来源的会话，不做猜测合并。
- 路由来源必须在现有 `Models` / `NetworkService` 中显式区分。远程联系人不能伪装成带服务器 IP 的普通 `PeerInfo`，发送文字和文件时不得误落入现有按对端 IP/端口建立 TCP 直连的路径。
- LAN 全员广播仍仅作用于局域网；不把本地广播、内网 IP、主机名或联系人自动同步到远程空间。不自动把旧私聊失败的内容转发到公网。

### 4. 远程协议与可靠性边界

- 保持既有 UDP 38888、TCP 38889 起始端口、`LANC` 魔数和旧帧字节结构不变。远程使用独立版本化封包，不能直接把旧二进制帧暴露为公网入口。
- 远程帧候选为 `[长度 UInt32 大端][类型 1 字节][负载]`，长度包含类型与负载、不包含长度字段；控制与文字负载候选为 UTF-8 JSON，后续文件块可用二进制负载。**先在阶段 1 确定三条真实产物均可用的编解码方案，再于阶段 2 冻结协议 v1**。不能把 `System.Text.Json` 当成当前原生四引用集已经具备的能力；如选型需要额外系统程序集，先明确引用变化和最低运行时、审核后才调整构建。未认证阶段、正文和块的长度上限须分别校验，先校验长度再分配内存，并正确处理拆包、粘包、EOF 和无效 UTF-8。
- 控制消息覆盖版本协商、认证、联系人/在线状态、文字、接收确认、错误和心跳；正文至少携带协议版本、消息 ID、目标设备 ID 和内容。发送者身份由服务端根据认证连接填入，不信任客户端自行声明的 `SenderId`、空间或权限。
- 第一阶段只在接收端在线时转发，不建立服务端离线消息队列。接收方离线返回明确错误；用户本地已保存的聊天记录不等于服务器可离线投递。
- 消息状态至少区分“发送中”“对端客户端已接收”“失败”“结果未知”。中继写出成功不是对端收到，缺少接收端 ACK 不得显示已送达；ACK 仅表示接收应用已接受，不表示人已读或历史已可靠写盘。现有历史保存会捕获异常，不能把它直接当作持久化成功凭据。
- 每个远程消息使用唯一 ID；在同一接收进程内维护有界去重缓存，键为 **稳定服务器标识＋空间标识＋服务端认证确定的发送者 DeviceId＋消息 ID**。不能仅按消息 ID 去重，避免两个发送者使用相同 ID 时误吞后一条消息；ACK 同样关联完整发送者/消息键。对同键重复消息重发 ACK、不重复上屏，缓存淘汰后不承诺继续去重。断线后自动恢复连接，不自动重放未确认正文；超时或断线存在“对端收到但 ACK 丢失”的不确定性，必须显示结果未知。首版可由用户重新发送为一条新消息；如以后加入复用原 ID 的手动重试，仍使用上述去重键，不能绕开缓存规则。跨进程重启的严格去重、保证恰好一次和持久化重试队列不作为首版承诺。
- 连接发送串行化，接收为独立循环；队列必须有界。连接时设置认证超时；读帧设超时/速率边界，避免半包永久占用连接。重连采用带随机扰动的指数退避；认证失败或协议版本不兼容停止自动重试。
- 建议先以 30 秒心跳、90 秒失联阈值、重连等待逐步增加至 60 秒作为待测参数，不沿用 LAN 8 秒广播/25 秒过期机制。服务器重启、网络切换和电脑睡眠唤醒后重新认证并同步在线列表。

### 5. 文件、安全和运维

- 在线文字验收后再加入在线文件中继；建议初始单文件上限 100 MiB、单设备同时 1 个传输、块大小 64 KiB，均为待压测参数，远程限制不缩减现有 LAN 文件能力。
- 文件必须经接收者明确接受，再开始转发；不得继承 LAN 默认自动接收行为。服务器不存整份文件、不按客户端给定的路径读写本机文件，只转发受授权的传输 ID、元数据和块。
- 每次传输绑定真实发送者、接收者、总长度和顺序；校验累计字节数并在完成时核验摘要。接收端仅使用安全文件名写入自己选择的目录，使用临时文件，成功后再完成命名；不能借文件名跨目录写入。
- 慢接收端必须反向限制发送端，限定所有应用层及流写出缓冲的总字节数；超时、取消、断线要释放传输状态。文字不得无限排队等待大文件，使用受限块调度与公平发送；如单连接队头阻塞无法满足交互目标，再评估单独文件连接，不先增第二通道。
- 服务级同时在途文件数、全部连接合计缓冲上限及各队列预算在阶段 3 定稿并压测，不能只靠“每设备同时 1 个文件”控制全服务内存。远程收文件事件携带认证发送者 ID 和完整会话键，不能复用 `FileTransferController.HandleFileReceived` 按昵称匹配、失败归入 BROADCAST 的路径；同昵称设备必须归入各自会话。
- TLS 最低要求为 1.2，优先使用系统支持的安全版本；验证证书链、名称及有效期，拒绝跳过校验。TLS 保护客户端到服务端链路，服务器仍可读取明文，首版不宣称端到端加密。[T1]
- 公网通道需独立认证、授权、速率与资源限制。**用户明确收口后，在归档决定与刷新记忆的同一步实际修改现有 `.claude/Rules.md` 第 6 条**：将其“可信纯内网、无恶意篡改、不做复杂握手”的适用范围限定为现有 LANC 局域网路径；明确公网中继需独立认证、授权、TLS 和限额。不能仅在决定正文补一句而保留规则原文的全局歧义，也不另写第二份 `Docs/` 基线。本轮仍只修订提案，进入公网代码实施前必须完成规则修订。
- 服务端建议由非 root 用户通过 systemd 托管，限制文件权限、连接数、队列和日志大小；低端口绑定采用最小权限，不长期以 root 运行 Python。部署包含防火墙、证书续期/重载、配置校验、版本回退和服务端元数据备份。SSH 仅供管理，旧 LAN TCP/UDP 端口无需在 VPS 开放。
- 提议先限制正文为 16 KiB UTF-8，单设备消息速率 5 条/秒、突发 10 条；暂以全服务 50 个认证连接为上限。未认证连接、TLS 握手、每 IP 连接及失败认证也需独立上限，不能只限制登录后的发送速率。参数依据资源验证修订，不宣称能阻止全部 DDoS。
- 统计实例出站流量和应用字节量，设置月度告警与可配置的文件传输预算；靠近预算时先拒绝新文件并保留文字容量，不自动升级套餐。应用计数不能覆盖系统、攻击及其他程序流量，不能保证账单绝不超过实例费；仍以 Vultr 控制台计量为准。[V2]

### 6. 实现边界

- 沿用现有 `NetworkService` 门面、`Models`、Presenter、设置与历史服务，不为远程另造一套聊天界面或复制 C# 核心。
- 新增长连接对象前，按规则第 5/10 条先评估职责与生命周期：独立对象仅负责远程连接、认证、收发与退出释放；不通过继续堆积 `partial NetworkService` 规避拆分要求。文件和方法命名在实施计划中确定。
- Windows 与 Linux C# 共享远程核心和协议 DTO；显式更新 Linux 项目源码链接。Python 使用同一协议和跨端样例，不引入运行时 pip 安装。JSON 使用标准序列化能力，不能以现有配置文件的正则抽取方式解析不可信网络帧。
- 服务端可以使用系统 Python 运行；客户端无需安装 Node、Docker、VPN 或新的大型运行库。编译器版本、目标 Framework、操作系统和实际 TLS 能力分开核对，不静默抬高支持下限。
- Windows 设置入口和会话来源标识仍遵守现有 GrokBot 设计规范；实现时按规则读取 Windows 上下文和 UI 规范，不提前重做窗口布局。

### 仓库已核实事实

| 文件 | 当前行为及对本案的影响 |
|---|---|
| `src/NetworkService.cs` | `LocalId = Guid.NewGuid().ToString("N")`；`AutoAcceptFiles = true`。需要远程稳定身份与独立文件接收策略。 |
| `src/NetworkService.Discovery.cs` | 本地广播/子网扫描、`ProbeIp`、固定基础端口 TCP 探测及 LAN 心跳过期。跨网段发现失败不等于无路由；中继可绕开对本地广播的依赖。 |
| `src/NetworkService.Interface.cs` | 虚拟网卡识别、源物理网卡优先绑定。远程连接应按系统出口路由，不直接继承此策略。 |
| `src/NetworkService.Transfer.cs` | 文本/文件直接连接对端 IP、解析 `LANC` 帧；收到文字先回旧协议 ACK，再触发事件，不能等同于远程确认与持久化成功。 |
| `src/Models.cs` | `PeerInfo` 以 IP/TCP 端口为通信定位；`ChatMessage` 无远程消息 ID 和送达状态。需显式扩展路由和远程状态，旧序列化保持兼容。 |
| `src/Controllers/ChatPresenter.cs` | 私聊直接调用 `NetworkService.SendTextMessage`；群聊枚举活跃节点。需防止远程联系人被 LAN 全员广播误选。 |
| `src/Controllers/SessionPresenter.cs`、`src/Services/SessionManager.cs` | 会话围绕现有 peer ID / BROADCAST 管理；远程键必须稳定且隔离。 |
