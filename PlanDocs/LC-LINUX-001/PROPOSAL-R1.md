# Linux 桌面版可靠性、会话历史与界面改进

**LC-LINUX-001 · 第 1 轮 · 提案方 Codex · 2026-11-18**

审计基线为 `main` 的 `a0e49c1`（`v2.0.16`）和本机同版本 `.deb`。

## 要决定的问题

用户要求逐项衡量 Linux 桌面版与 Windows 的差距，提出能改善界面和日常体验的方案。本轮请审核首批修复的范围、Tkinter 改造的可行性、图标后端与规则的符合性，以及能在真实 Linux 桌面验收的交付条件。

### 功能对照

以实际接通的 Windows 桌面操作为参照，选取 24 项。基础路径可用列有 6 项，部分实现列有 8 项，缺失列有 10 项。这是按入口和交互核对的审计样本，同机验证的范围见「证据」。

| 模块 | 基础路径可用（6） | 部分实现（8） | 缺失（10） |
| --- | --- | --- | --- |
| 发现与连接 | 基础局域网发现 | 手动 IP 直连的结果反馈 | 多网卡发现及物理网卡绑定 |
| 会话与历史 | 昵称和 IP 搜索 | 未读与焦点提示、切回群聊后的重绘 | 重启后恢复、离线会话及同 IP 重连归并 |
| 文字 | 私聊、群聊 | 私聊的失败反馈 | 表情选择器 |
| 文件 | 打开接收目录 | 私聊单文件收发、进度及结果、自动接收开关 | 多选与拖拽、卡片打开文件及定位、自定义接收目录 |
| 桌面与设置 | 昵称修改并保存 | 检查更新后跳转下载页 | 托盘与桌面提醒、分类设置、主题／强调色／独立字体 |

Linux 桌面评估对象为 `.deb` 启动的 Python/Tkinter。Python `--cli` 和自包含 x86_64／ARM64 ELF CLI 属于单独的回归入口。

## 建议决定

### 1. 现有桌面入口先修可靠性

- 群聊重绘先分辨系统、文字及文件消息。私聊切回群聊和窗口缩放后保留完整消息流。左侧「会话」上明确当前导航反馈，自动接收控件从实际配置初始化。
- 私聊发送结果回到发起会话。等待期间与最终成功或失败可区分，切到另一会话时结果仍归原会话。直连给出验证、等待、成功或失败反馈。收到的文件按发送者 ID 和连接端点归属，两位同名联系人各自收到正确的记录。
- 文件发送以接收端明确确认落盘为成功。拒收、连接失败、超时和异常应结束进度并显示原因。群聊内的既有文件入口改为选择在线接收者，文案与 Windows 已接通的选人行为一致。保持现有 64 KiB 流式传输。
- 在现有 Python 协议读取器处理 TCP 短读，覆盖魔数、定长头字段及现有字符串读取行为。回归 LANC 文字／文件帧、端口和 ACK 的既有语义。沿用工作线程到 Tk 主线程的事件队列，网络回调携带来源和操作标识。

### 2. 让会话在节点和应用重启后可找回

- 对齐 Windows 的局域网会话语义。已确认的局域网 IPv4 用于会话归档，当前在线的 ID、地址和端口用于路由，群聊有独立键。证据不足的记录保持各自归属。发送者昵称用于展示及搜索。
- 用轻量 JSONL 在当前用户或便携数据目录保存文字、时间、对端身份和文件属性，沿用已存在的配置读写与目录回退边界。验证旧设置含缺失字段、路径无法写入、重启、重复读入、尾部不完整记录及同名不同 IP。正在发送的临时状态在重启后须有符合实际的显示。
- 离线会话显示档案昵称、历史及可读取的文件路径。在线节点换实例 ID 后继续进入原会话。相同 IP 被不同设备重新分配时沿用现有 Windows 局域网规则的边界，验收记录该限制。

### 3. 用现有 Tkinter 做 GrokBot 双栏

- 左侧一栏集中搜索、连接节点、在线／离线会话、未读和个人入口。右侧集中标题、圆角聊天气泡、文件卡片和输入胶囊。按 [GrokBot 设计规范](../../Docs/GrokBot_UI_Design_System.md) 使用 `#0E0E0E` 侧栏、`#121212` 聊天底色和 `#202024` 输入底色。输入胶囊 64 px、圆角 32 px，附件钮 36 px、发送钮 44 px，正文按 11 pt 使用高对比文字。按缩放后的逻辑尺寸检查。
- 会话列表及聊天流复用一套暗色浮动滑块交互，静止 4 px、悬停或拖动 5 px、无溢出隐藏。保留原生文本输入的焦点、中文输入法、粘贴和换行，圆角容器、气泡和按钮由 Tk 绘制层承担。先验证选中会话、滚动位置和键盘可达性，再把重复的头部及工具栏动作收进菜单。
- **图标需单独判定。** [项目规则第 9 条](../../.claude/Rules.md) 明写 GDI+ 矢量绘制。优先评估用现有 [WeChatIcon.cs](../../src/UI/Renderers/WeChatIcon.cs) 在构建期生成少量随包或嵌入单文件的多倍率图标，保持轮廓、线宽、圆端点、主题色和轻量部署。请审核方判断它是否符合现行规则。若规则要求每次运行时由 GDI+ 绘制，则由用户决定是否允许采用 Linux 原生等效后端。此决策影响正式 UI 接入，前两步可独立推进。
- 第一批分类设置优先支持修改接收目录、自动接收及历史管理。主题、强调色和独立字体在基本布局和缩放验收后接入。建议沿用 Python 单文件发布方式，先按网络服务、会话状态和可复用控件划清职责，评估实测复杂度后决定拆分方式。

## 建议顺序

| 步骤 | 交付 | 验收口径 |
| --- | --- | --- |
| 1. 修复主流程 | 群聊重绘、私聊和直连反馈、文件归属及结果、选接收人、自动接收状态 | 启动、切回群聊、缩放均正常重绘。可达和不可达私聊各有明确结果。切换会话后结果仍归原处。文件逐字节一致，拒收、断开与失败不会进入成功态。分段读取及 Python ↔ C# 双向互通回归。 |
| 2. 接通会话历史 | 本地记录、离线查看、当前节点重连、文件选择器多选、文件卡片操作及接收目录 | 应用和对端分别重启后消息仍可查。同名两机各归原会话，同 IP 换 ID 后连续。多选的文件各自反馈收发结果。已有配置可读，目录错误有反馈，清理范围与确认文案一致。 |
| 3. 主窗与设置改造 | 双栏主界面、圆角输入、消息气泡、浮动滑块、分类设置 | 真实 Linux 桌面使用截图逐项对照规则。窄窗及缩放下入口完整、滚动可操作、输入法和键盘可用。重跑步骤 1、2 的主要路径，验证桌面包和两类 CLI。 |

建议在第 1 步完成后做一次独立代码审核，第 2、3 步各自验收，再决定是否将三步合并交付。实机尚未取得的证据应体现在交付状态里。

## 明确不做

本话题的交付范围为内网 Linux 桌面主流程与视觉对齐。跨网通信、批量群发、托盘、原生文件拖拽、表情选择和完整多网卡对齐均是后续可独立决定的话题。Windows 作为互通与视觉验收基线，现有 LANC 协议、Windows 原生轻量构建及三种 Linux 分发入口属于首批兼容约束。
